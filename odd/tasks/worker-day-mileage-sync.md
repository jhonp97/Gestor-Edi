# Worker-day editing and truck mileage sync

## Goal and authorization
User wants to edit already-marked workdays from the Workers section, setting company and per-truck kilometers, and have those kilometers appear in Truck Mileage history and all mileage statistics/reports. User selected the conflict rule: **avoid double counting; link derived mileage to its workday; when a manually entered TruckMileage row already exists for that truck/date and the operation supplies km, reject atomically and ask the owner to reconcile it—never silently add or overwrite.**

## Confirmed existing architecture
- Worker detail `/workers/[id]` has a read-only `DailyPayPanel`; it displays operation details and currently says edit from truck detail.
- Truck detail already hosts `WorkerDayOperationEntry`, with GET/PUT to `/api/workers/:id/operations/days/:date`; it edits company and up to two truck segments (share, km, incident).
- `WorkerDayTruckSegment` has optional Decimal kilometers, one row per truck/date; `TruckMileage` is a separate Float row, also unique per truck/date.
- Truck stats, mileage history and monthly PDF read/sum `TruckMileage`; saving a worker-day currently never updates it.
- Worker operation writes are Serializable and reject PAID months. Preserve this lock and tenant ownership.
- On operation update the repository deletes/recreates segments inside one transaction. This permits linked derived mileage to cascade with its source segment and be recreated atomically.

## Accepted design
- Add an optional unique `TruckMileage.sourceWorkerDaySegmentId` FK to `WorkerDayTruckSegment`, inverse relation, with `onDelete: Cascade`; null means manual mileage, non-null means generated from that segment. New additive migration only; do not apply it to any database here.
- In the same worker-day Serializable transaction, before deleting old segments, detect a conflicting manual mileage row for any target truck/date with supplied kilometers. Return a clear 409 before any change. Existing linked rows are safe to replace. After creating each segment with non-null persisted kilometers, create exactly one linked TruckMileage from the persisted Decimal value. Removing a segment or clearing its kilometers removes only its derived record; never delete/overwrite a manual record.
- Keep derived mileage protected from manual deletion through the mileage API/UI; show its source clearly in truck history. Existing totals and monthly PDF already sum TruckMileage, so linked entries flow into them once.
- Add an Edit operational details control to the selected marked day in the Workers/DailyPay section, reusing `WorkerDayOperationEntry` with worker/date and existing primary truck prefilled. On save, refresh day detail, worker panel and router data. Preserve share totals, replacement rules and paid-month lock.
- For a legacy marked day with no operation, never infer company/truck from current worker assignment. Keep the existing explicit confirmation, and require the owner to select the historical primary truck before attaching company/km details.
- Do not backfill historical segment kilometers in bulk; a user editing/saving that workday attaches the current values. This avoids silently colliding with manual mileage.

## Acceptance
- Editing company/segment/km from Workers preserves the historical day/rate and applies the same PAID lock.
- All writes to segments and derived TruckMileage are atomic and tenant scoped.
- Exactly one derived TruckMileage exists for each non-null-km segment, keyed by its source segment; replacement/removal cleans the old generated row and creates only the current one.
- Existing manual row plus supplied operation kilometers returns conflict without changing existing workday, mileage or stats; no data lost/doubled.
- Missing km creates no derived mileage; explicit zero remains a recorded zero; persisted two-decimal value and mileage stats agree.
- Derived rows appear in Truck Mileage history, totals and monthly PDF once, identify their operational source, and cannot be manually deleted. Manual mileage remains editable/deletable under existing permissions.
- UI exposes prefilled edit only for a verified operational day; failed detail loads never show stale editor data; successful save refreshes the daily-pay display and truck/mileage statistics.
- Synthetic tests cover manual-vs-linked rows, serialized rollback, edit with company change, two-truck replacement, cleared km, paid month, missing auth/tenant, route delete guard and UI cancel/success/conflict.
